# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`healthd` — a single Go binary that syncs Google Health (watch/phone data) and Cronometer (nutrition) into one encrypted local SQLite database, and serves a dashboard over it. No third-party cloud service sits between the user's data and them.

**Read these docs before making non-trivial changes — they are kept current and are more detailed than this file:**
- `ARCHITECTURE.md` — the *why*: design intent, encryption, sync model, UI approach.
- `structure.md` — the *where*: repo layout, package responsibilities, how packages connect.
- `prerequisite.md` — environment gotchas and findings from past sessions. **Read this first**, it will save you from repeating already-diagnosed mistakes.
- `cronometer-integration.md` — how the Cronometer integration specifically works (client, auth, sync, UI, known gaps).

## Commands

```bash
make generate        # templ generate — compile .templ files into Go (_templ.go)
make build            # generate + go mod tidy + go build -o bin/healthd ./cmd/healthd
make run              # generate + go run ./cmd/healthd (foreground dev run, no artifact)
make test             # go test ./...
make vet              # go vet ./...
make fmt              # gofmt -l -w .
make clean            # rm -rf bin/
```

Run a single test: `go test ./internal/cronometer/ -run TestSyncDayIsIdempotentOnRepeatedRuns -v`

**Critical gotcha**: `go build ./...` does NOT produce `bin/healthd` — it only typechecks. After editing code (and running `templ generate` if `.templ` files changed), you must explicitly `go build -o bin/healthd ./cmd/healthd` (or `make build`) and restart the running binary before a change actually takes effect. Running the old binary after a "successful" `go build ./...` looks fine but silently serves stale behavior.

Never hand-edit a `*_templ.go` file — it's regenerated by `templ generate` and says so at the top.

### Local/manual testing

Never seed, wipe, or `db init` against `bin/explore-root` — it's the user's real configured `--root` with real synced data landing in it independently of any test session. For any live verification, use an isolated scratch root instead:

```bash
HEALTHD_DB_PASSPHRASE=throwaway ./bin/healthd --root <scratch-path> db init
./bin/healthd --root <scratch-path> serve   # dashboard only, port 8080 by default
```

`healthd serve` runs only the web dashboard, not the sync scheduler (see Architecture below) — use the dashboard's Sync button, `healthd sync`, or a throwaway script against `internal/db.Open` to get real-shaped data into a scratch root without live credentials.

## Architecture

One Go module (`github.com/sdhungan/Personal-Health-Data`), one binary (`healthd`, entrypoint `cmd/healthd/main.go` → `internal/cli.Execute()`), built with Cobra + Echo + templ + Datastar.

**Subcommands**: bare `healthd` (2026-08-05: runs EVERYTHING as one process now — web dashboard as the main loop, sync scheduler as a ticker goroutine, all sharing one `*db.Store` — see `ARCHITECTURE.md` §2; there is no more `healthd serve` subcommand, merged into this), `healthd sync` (one-shot immediate sync, both sources), `healthd auth google` / `healthd auth cronometer`, `healthd db init` / `healthd db decrypt <out.sql>`, `healthd mcp --user <username>` (local stdio MCP server exposing Cronometer food search/logging tools to Claude Code/Desktop — moving this to an HTTP route on the merged process was tried and reverted the same day, see `ARCHITECTURE.md` §11 — its dish-vs-single-item tool policy still applies regardless of transport), plus `--action=install/start/stop/uninstall` for the one OS-service lifecycle via `github.com/kardianos/service` — systemd on Linux, Windows Service on Windows — with `--service-name` to override the registered name (default `healthDSafal`); installing requires an elevated/Administrator shell on Windows, root (or an equivalent systemd/sysv-managing user) on Linux. `--google-client-secret <path>`, if given and valid, is the only way to (re)configure the app-wide Google OAuth client — see `web.GoogleClientLockedByFlag`. Every run also writes structured logs (zap) to `<root>/logs/healthd.log` (`internal/applog`), rotated past 1000 lines.

**Resolved gap** (2026-08-05): the scheduler and the dashboard no longer need to run as two separate processes to get "always-on with auto-sync" — see the Subcommands entry above.

**Data flow**: Google Health API + Cronometer mobile API → sync job (internal `robfig/cron` scheduler, or manual trigger) → writes `watch_*`/`cronometer_*` tables in the encrypted SQLite DB (source of truth) → `internal/web` reads via `database/sql`, builds `views` structs → templ components render HTML, patched into the page via Datastar SSE. `internal/db.Store` is the only thing that ever has the DB in plaintext on disk, and only for the life of one run (whole-file AES-256-GCM encryption, key derived via Argon2id).

**`_raw`/`_override` column split** (watch_* tables only, e.g. `body_measurement.weight_kg_raw`/`weight_kg_override`): the sync job is the *only* writer of a `_raw` column; UI edit endpoints are the *only* writer of an `_override` column; reads resolve `COALESCE(_override, _raw)`. Never have UI code write a `_raw` column. `cronometer_*` tables have no such split — Cronometer sync is the sole writer of those outright, since nutrition data has no UI edit path.

**`watch_*` schema — five fixed representation shapes** (see `schema.sql`'s header comment for the authoritative version): DailyScalar, DailyByCategory, Hourly, Timeline, SegmentTimeline. Session types (sleep, exercise, ECG) don't fit any shape and are bespoke tables. Picking a shape for a new metric means asking how its values are actually useful to look at, not just what the API can return.

**Package map** (see `structure.md` for full detail on each):
- `internal/paths` — the only place that builds a path under `--root`.
- `internal/config` — `config.yaml` loading, overlaid on defaults.
- `internal/crypto` — AES-256-GCM + Argon2id, used by both `internal/db` and `internal/googleauth`.
- `internal/db` — schema (`schema.sql`), `Store` (encrypted DB lifecycle: Init/Open/Checkpoint/Close/Discard), `dump.go` (the `db decrypt` export), `migrations.go` (mechanism exists, currently empty — the schema was rewritten wholesale once rather than migrated; populate this for the *next* real schema change).
- `internal/healthdata` — dependency-free plain Go structs mirroring `watch_*` tables; deliberately has zero internal-module dependencies so both `internal/googlehealth` (writer) and `internal/web` (reader) can import it without a cycle.
- `internal/googleauth` — OAuth2 local-redirect flow, encrypted token storage, auto-refreshing `http.Client`.
- `internal/googlehealth` — REST client (`health.googleapis.com/v4`), data-type catalog, `DBSyncer.SyncDay` (fetch + upsert per shape), diagnostic dump tool backing.
- `internal/cronometer` — mirrors `googlehealth`'s shape but for `mobile.cronometer.com/api/v2/*` (reverse-engineered mobile REST API, not the GWT-RPC library originally planned — see `cronometer-integration.md`). Session/credential handling with two separate encrypted files (long-term credentials vs. short-lived session token). `actions.go` adds food search/logging methods (`SearchFood`/`CreateCustomFood`/`LogServing`/`Diary`/`DeleteServing`) on `DBSyncer`, backing `internal/mcpserver`.
- `internal/syncengine` — source-agnostic day-completeness state machine (pending/partial/complete/missing); `googlehealth.DBSyncer` and `cronometer.DBSyncer` both implement its `DaySyncer` shape without importing it directly.
- `internal/mcpserver` — thin MCP tool layer (via `github.com/modelcontextprotocol/go-sdk/mcp`) over one `cronometer.DBSyncer`'s food actions, run over stdio by `healthd mcp` — see `ARCHITECTURE.md` §11, including the explicit dish-vs-single-item tool-use policy in `consumerInstructions`.
- `internal/cli` — Cobra command tree; `root.go` resolves `--root` once into a shared `*paths.Paths`; `run<Source>SyncOnce` helpers are shared between the one-shot `sync` command and the scheduler.
- `internal/web` — Echo server, routes, handlers, per-tile data builders (`data.go`, `bodymeasurement.go`, `foodlog.go`, `cronometer.go`, `journal.go`); no ORM, plain `*sql.DB` throughout. New DB-backed features follow the existing pattern: a small package file with fetch/save functions plus a struct in `views/models.go`.
- `internal/web/views` — templ components + plain-Go view-model structs; nothing here touches `*sql.DB`. `chart.go` renders server-side inline SVG (no client-side charting lib). Values-only confidence tiers (CONFIRMED/DOCUMENTED/INFERRED) are used throughout `googlehealth/values.go` and `cronometer/values.go` — don't guess a field name, a wrong guess silently decodes to a zero value instead of erroring.

**Multi-user accounts** (since 2026-08-02, see `ARCHITECTURE.md` §10): every table carries a `user_id` folded into its primary key. `internal/webauth` handles dashboard login (bcrypt password check + a 24h sliding-inactivity cookie session in `web_session`, gated by Echo middleware on every route) — this is entirely separate from provider auth: the background scheduler fans out one goroutine per user per source regardless of who's logged in, decrypting each user's Google/Cronometer credentials with a key derived from *their* account password (`keys/users/<id>.key`, cached to disk the same way the root `keys/db.key` already is, so unattended sync keeps working). Any new query needs a `userID` parameter sourced from `webauth.CurrentUserID(c)` — never a request parameter — this is the actual per-account isolation boundary, not the schema alone. CLI provider-auth commands now take `--user <username>`; `healthd user create <username>` makes an account headlessly. An account can also delete itself and every row of its own data from `/settings/account` (password re-confirmation required) — see "Account settings & deletion" below.

**UI stack**: templ (compiled Go templates, typos caught at `go build` time) + Echo (routing/HTTP) + Datastar (SSE-driven DOM morphing via the Go SDK's `ServerSentEventGenerator`, no client-side framework or state). One shared click-to-detail overlay (`#detail-overlay`/`$detailOpen` in `layout.templ`) backs both the activities list and the food log. The dashboard header's user-menu dropdown (avatar button → Account/Google settings/Log out) is also Datastar-driven (`$userMenuOpen`, toggled + click-outside-closed via a transparent backdrop — same pattern as the detail overlay). The login/signup/onboarding/settings/account pages are all plain server-rendered HTML forms (no Datastar) — full-page POST+redirect flows, not live-patched; they still get the light/dark theme (see below), just not SSE morphing.

## Account settings & deletion

`/settings/account` (distinct from `/settings/google-client`, which is app-wide) shows the current username and a self-service "delete my account and all data" action, gated behind re-entering the account password (`internal/web/account.go`'s `handleAccountDelete` — never a request parameter for which account, always `webauth.CurrentUserID(c)`). Deletion (`webauth.DeleteUser`) explicitly `DELETE`s every `user_id`-scoped table by name (`userDataTables` in `internal/webauth/users.go`), rather than relying on `schema.sql`'s `ON DELETE CASCADE` on every one of those foreign keys — SQLite's foreign-key enforcement is a per-connection `PRAGMA`, and Go's `*sql.DB` pools multiple physical connections, so there's no guarantee any given statement lands on a connection that ever had it turned on. If you add a new `user_id`-scoped table, add it to `userDataTables` too (or, for the one exception, `watch_sleep_stage`, which has no `user_id` of its own — see that function's own comment for the subquery-through-`watch_sleep_session` pattern). After the DB transaction, it also removes `keys/users/<id>.key` and `config/users/<id>/` from disk, and the caller (`handleAccountDelete`) is responsible for evicting that user's cached syncers from `web.Server`'s in-memory maps and clearing the request's cookie — `DeleteUser` only owns DB + on-disk credential state.

## Light/dark theme

Client-only, per-browser preference — not stored server-side, since it's cosmetic and has no bearing on any account's data. `layout.templ`'s `themeScript()` (an inline, synchronous `<script>` reading `localStorage.getItem("healthd-theme")`, defaulting to `"dark"`) is included in **every** full-page `<head>` — login/signup/settings/account/onboarding/the dashboard shell — so the chosen theme is consistent everywhere and never flashes the wrong one on load. `ThemeToggleButton()` (dashboard header only) flips `data-theme` on `<html>` and persists it; `style.css`'s `:root` (dark, default) and `:root[data-theme="light"]` blocks hold two **independently validated** categorical palettes (light and dark each get their own tuned lightness/hue steps against their own surface — see `references/color-formula.md` in the `dataviz` skill; running `scripts/validate_palette.js` against one mode's palette says nothing about the other). **Adding a new full-page templ file must include `@themeScript()` in its `<head>`** or that page will ignore the user's chosen theme.

## Empty tiles

A tile with no data for the selected day is never shown at full size (see `shouldHideEmptyTile` in `internal/web/handlers.go`) — its title is instead collected into `DashboardData.MissingByCategory[category]` and every dashboard section renders at most one compact `EmptySummaryTile` (`dashboard.templ`) listing what's missing for that section, e.g. "No data today: Blood Glucose · Core Body Temp", instead of either a full-size empty placeholder per metric or the whole section silently vanishing and leaving an inconsistent gap. `Body Measurements` is still exempt (always shown, it's an input form) and never contributes to the missing list.

**Datastar gotcha**: this project vendors Datastar v1.0.2 (JS runtime — not the `datastar-go` SDK version in `go.mod`). Never combine `data-show` and `data-attr:style` on the *same* element — causes an infinite reactive loop that hangs the page's JS thread. Fold the show/hide condition into the `data-attr:style` expression instead (see `chart.go`'s `renderChartOverlay`/`hoverAttrs` for the working pattern). Also verify Datastar syntax against `data-star.dev/reference/attributes` before writing it rather than from memory — it's young and fast-moving (e.g. `data-signals` multi-key init uses unquoted object-literal keys).

## Repo layout notes

- `cmd/healthd` — the only entrypoint. `cmd/cronodump` — real diagnostic dump tool for Cronometer's API. `cmd/cronoverify` — round-trips Cronometer's write endpoints against a real account; the tool `cronometer-integration.md`'s "Write endpoints" section names as the way to close out `DeleteEntries`'s still-open DOCUMENTED→CONFIRMED verification.
- `Creds/` and `bin/` are gitignored. `bin/explore-root/` is the user's real dev `--root` — see the gotcha above. `Creds/` is not read by the app itself — it's just a convenient gitignored place to keep a downloaded `client_secret_*.json` before uploading it (see the Google OAuth client setup note below).

## Google OAuth client setup

The Google OAuth *client* JSON (`client_secret_*.json` from Google Cloud Console) is not picked up automatically from any folder — dropping it into `Creds/` alone does nothing. Three ways to set it, none mutually exclusive:

```bash
./bin/healthd --root <root> serve --google-client-secret Creds/client_secret_....json  # re-saved on every serve startup
./bin/healthd --root <root> google-client set Creds/client_secret_....json             # one-off, no server restart needed
```

...or the dashboard's `/settings/google-client` upload form. `--google-client-secret` is optional, not required — a fresh `--root` still runs `serve` fine without it, just with Google Health unconfigured until one of the three happens. All three validate the file, encrypt it with the root DB key, and write it to `config/google_oauth_client.json.enc` — see `internal/googleauth.SaveClientJSON`/`ARCHITECTURE.md` §5 and §10. It's an app-wide setting (one Google Cloud project serves every account's own "Connect Google Health"), not per-user. Once the client is configured, `/settings/google-client` also lets the *currently logged-in* account connect its own Google Health right there (not onboarding-only — see that page's own doc comment for why the two live together; this is the fix for a real gap: fixing the client JSON used to strand you with no way back to the per-account consent flow except navigating to `/onboarding/connect` by hand). Two things Google-side that a correctly-configured client won't fix: the Google Health API must be enabled on that Cloud project, and — if the OAuth consent screen is still in "Testing" publishing status — your Google account must be added as a test user, or the consent flow fails with "access blocked."
